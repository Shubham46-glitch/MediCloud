# Amazon S3 document storage

## What the code implements

`backend/src/adapters/storage/s3-storage.adapter.js` stores medical document bytes in S3 when `STORAGE_PROVIDER=s3`. Source defaults the bucket name to `medicloud-medical-files-0234` and region to `ap-south-1`; the supplied deployment context names the same bucket in `eu-north-1`. The bucket, region, privacy controls, encryption settings, and CORS configuration are not verified in AWS.

Objects use `medical-records/<userId>/<uuid>-<sanitized-filename>`. The adapter accepts PDF, JPEG, PNG, and WebP up to 10 MiB, signs PUT for 900 seconds, and signs GET for 300 seconds. Upload signing includes the submitted content type and size and requests `AES256` server-side encryption. The browser sends that encryption header. Confirm browser PUT compatibility and signed headers with an actual non-sensitive upload; bucket default encryption, KMS, public access block, and actual encryption behavior are AWS-side settings requiring inspection.

## Upload, retrieval, deletion

1. Authenticated browser calls `POST /api/documents/upload-url` with filename, MIME type, size, and optional description.
2. API validates values, signs a URL with a server-generated key and stores an owner-bound upload intent with expiration.
3. Browser uploads file bytes directly to S3 using `PUT`, `Content-Type`, and `x-amz-server-side-encryption: AES256`; the browser does not send file bytes through Express.
4. Browser calls `POST /api/documents/confirm-upload` with `uploadId`. The API reads the user's intent, runs `HeadObject`, compares content length/type, then transactionally records metadata and consumes the intent.
5. For download, API checks the metadata key under the authenticated user's partition, verifies the object with `HeadObject`, and returns a 5-minute presigned GET.
6. For delete, API calls S3 `DeleteObject`, then soft-deletes the DynamoDB metadata item.

Presigned URLs are bearer credentials. Do not log, paste into tickets, or share them. URL expiry does not revoke a URL before its expiration.

## CORS and bucket setup

Keep S3 Block Public Access enabled. In the bucket's **Permissions > Cross-origin resource sharing (CORS)** setting, allow only the exact deployed frontend origin and `PUT` for this upload flow. The signed browser request includes `Content-Type` and `x-amz-server-side-encryption`; an example document is:

```json
[
  {
    "AllowedOrigins": ["https://<approved-frontend-host>"],
    "AllowedMethods": ["PUT"],
    "AllowedHeaders": ["content-type", "x-amz-server-side-encryption"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3000
  }
]
```

This is a template; add any headers actually present in the browser request and validate in the S3 Console. CORS permits the browser request; IAM and the signature authorize it. Never make the bucket public to address a browser CORS error.

## IAM and data controls

The backend role needs object-level `s3:PutObject` to sign uploads, `s3:GetObject`/`s3:HeadObject` (authorized through GetObject) for checks and signed retrieval, and `s3:DeleteObject` for deletion. `s3:ListBucket` is not used by the shown adapter. Scope object actions to `arn:aws:s3:::<bucket>/medical-records/*`; bucket-level settings/actions use `arn:aws:s3:::<bucket>`. Confirm actual role policies in AWS. Protect documents with Block Public Access, bucket-owner controls, suitable encryption, logging/monitoring, lifecycle and retention decisions, and tested recovery. Do not infer compliance from these settings.

## Failure recovery

- If upload succeeds but confirmation fails, retry confirmation while the intent remains valid. If it is expired or removed, an operator can reconcile the owner-scoped object against the intent/metadata before deleting an orphan. Avoid broad bucket scans or exposing object keys.
- If metadata is created but object availability changes, the download endpoint returns not found after `HeadObject`; reconcile metadata with the object.
- If S3 deletion succeeds but metadata soft-delete fails, mark/reconcile metadata after confirming the object is absent. If S3 deletion fails, metadata remains active; repair permission/connectivity and retry.
- A missing object may appear as 404 or an access failure depending on caller permissions. Check CloudTrail and the role identity before concluding it is absent.

Test with a non-sensitive file and the deployed origin. CORS success has not been independently verified.
